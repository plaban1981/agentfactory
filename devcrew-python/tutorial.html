A Python port of the DevCrew AI dev-team: four role agents built on LangChain Deep Agents take a task through analysis, development, review and testing. 1Problem statement

Why a single autonomous coding agent is not enough — and what an agent factory adds.

The naive approach

Point one model at a ticket and let it edit main. It works in a demo — then reality bites: no one reviews the diff, a runaway loop bills your card overnight, a prompt hidden in an issue hijacks the session, and there is no record of who (or what) changed what, when, or why.

The factory approach

Split the work across specialised roles (Analyst → Developer → Reviewer → Tester), run each role inside a bounded loop (turn limits, per-agent monthly budgets), require a structured submission per stage (submission is not completion), enforce mechanical checks a model can't talk its way around, and write every spend and transition to a ledger.

Use case 1 · Demo & teaching

--mode offline runs the full pipeline on a deterministic scripted model — no API key, no network, no cost. Every stage, gate and ledger entry is exercised exactly as in live mode.

Use case 2 · Real development assistance

--mode live swaps in anthropic/claude-sonnet-5.5 via OpenRouter. The same guards apply: budgets, protected paths, rework rounds, manual or auto merge.

Use case 3 · Governance evaluation

The trust scan, budget ledger and failure-mode tests make the repo a testbed for "how do we keep autonomous agents inside the lines?" — the question an agent factory answers.

What this port is — and isn'tIt is a faithful logic port of the DevCrew TypeScript app (lib/task-runs.ts, agent-tools.ts, agent-defaults.ts, agent-budget.ts) to Python with Deep Agents. It is not the Cloudhike/Next.js deployment: jobs run inline in one process (the original's own dev fallback) and the repository backend is a local git checkout with the same rules, not the GitHub API.

4End-to-end execution

What happens, in order, when a task is created and run with auto-merge — and exactly which code runs at each point.

  1. 1

    Task lands on the board

    add_task(store, title, description, type, priority) numbers it (DC-1) and files it in Todo. Nothing runs yet — a task is data, not intent.

    factory.py › add_taskUI: POST /api/tasks
  2. 2

    Run starts with a budget pre-check

    start_task_run creates the TaskRun (stage analysis, round 0), checks every team member's monthly balance (25¢ minimum) and emits run_started. In the UI this happens on a worker thread; the API returns immediately.

    pipeline.py › start_task_runbudget.py › assert_can_run
  3. 3

    Analysis — the Analyst explores and plans

    A Deep Agent graph runs with the Analyst's verbatim instructions, read-only repo tools and hand_in_analysis. The structured result — problem, approach, files to change, risks — becomes run.plan. Without a valid plan the stage cannot complete.

    agents.py › build_stage_agent("analysis")tools.py › parse_analysis
  4. 4

    Development — branch, commits, submission requires real work

    The branch feat/dc-1-<slug> is created from the default branch (run-id suffix on collision). The Developer gets all five repo tools; each write_file/delete_file is one commit on the branch. The validator rejects hand_in_work until the branch is 0 commits behind/ahead-clean — submitting with no commits raises "You haven't committed any changes yet" back into the agent loop.

    pipeline.py › development validatorrepo.py › compare_branches
  5. 5

    Review — approve, or send it back

    The Reviewer sees task + plan + diff and answers approved with a summary or changes_requested with required changes. A rejection increments run.round and returns the run to development. Round 3 fails the run: "needs changes after 2 rounds".

    tools.py › hand_in_reviewMAX_REWORK_ROUNDS = 2
  6. 6

    Testing — the Tester verifies, then DevCrew double-checks

    The Tester submits a pass/fail with checks. Even on "pass", the pipeline overlays six mechanical branch checks — branch exists, separate from default, has commits, files changed, planned files touched, no protected files. DevCrew's checks overrule the Tester: a model saying "pass" cannot excuse a branch with no commits.

    pipeline.py › branch_checksrepo.py › is_protected_path
  7. 7

    Pull request

    The diff is measured (files, +/− lines) and a PullRequest artifact is recorded: number, title DC-1: …, state open. In auto mode the run advances to merge; in manual mode it stops here — the card sits in Testing with run status done until a human merges and drags it.

    pipeline.py › pull_request_stage
  8. 8

    Merge — or a filed follow-up

    Auto mode merges locally. On conflict the PR is marked blocked and the Tester files a follow-up task ("Resolve merge conflicts for DC-1", high priority) in Todo. On success the card moves to Done and a task_completed ledger entry is written.

    pipeline.py › merge_stagerepo.py › merge
  9. 9

    Every step is priced and recorded

    After each stage, record_agent_spend writes ceil(cost) cents against the acting agent's month, warning at 80% of cap. Stage starts, reviews, test runs, PRs and errors all append to activity.jsonl, and each transition is emitted to the WebSocket event sink for the UI feed.

    state.py › save_ledgerui/app.py › Broker.publish
Design principleSubmission is not completion. A model's claim of success is always validated mechanically — commits must exist, branches must be ahead, protected paths must be untouched — before the stage machine advances.

6Guard rails: budget, trust, rework

Three independent mechanisms keep the agents inside the lines. Each is fail-closed: an exception means the stage — or the run — stops.

The stage loop and rework gate

Review and testing can each send work back; the third strike ends the run. The budget check fires before every model invocation, not after the money is spent.

The six trust checks

1
Clear role and workflow · 20Instructions define the role and numbered steps; too short to steer an agent = fail.
2
Prompt-injection guardrail · 20Repo content, issues and tool output are treated as data, never instructions. Absent = fail.
3
Secrets protected · 15Never print/commit secrets, tokens or .env values. Absent = fail.
4
Approval for high-impact tools · 20Shell / apply_patch / computer_use require human approval. Absent = warn.
5
Budget cap · 10Monthly budget ≤ $1,000, else warn — a runaway loop must have a ceiling.
6
Skills match the role · 15Attached skills overlap the role's defaults; none attached = fail.

Pass = full weight, warn = half, fail = 0. The default team scores 100/100; python -m devcrew.cli trust re-runs the scan with findings.

Budget middleware

before_model and wrap_tool_call call assert_stage_budget: spend is estimated from real OpenRouter usage metadata (via CostTracker) and recorded with ceil(cost) cents per stage. Cap reached → BudgetExceeded; 80% → budget_warning ledger entry.

Turn limits

ModelCallLimitMiddleware(run_limit=max_turns, exit_behavior="end") ends the agent gracefully at its turn cap (Analyst 20 · Developer 60 · Reviewer 20 · Tester 15) instead of looping forever.

Single submission

A SubmissionBox accepts exactly one outcome per stage; a second hand_in() raises "You already submitted." The agent loop only ends when the model stops calling tools — a GraphInterrupt raised inside a tool is swallowed by the runtime, so validation errors are returned as tool text instead.

Why scripted offline mode mattersScriptedChatModel replays deterministic tool-call scripts through the exact same pipeline, middleware, validators and ledger. All 32 tests and the WS smoke test exercise the governance machinery with zero network and zero cost — the guards are testable without the model.

7The web control room

A FastAPI + WebSocket replacement for the original's Next.js office/board views. One demo workspace, one run at a time, everything streamed live.

State

GET /api/state returns the full snapshot: agents (trust score, monthly spend vs budget bar, status dot), tasks, runs, PRs and the 80-entry ledger tail. POST /api/reset recreates the demo workspace — sample-repo seeding is idempotent.

Actions

POST /api/tasks creates a task; POST /api/run {task_id, mode} starts it on a worker thread (409 while busy, 400 for live without a key). The pipeline's event_sink is the broker's publish(), called thread-safely from the run thread.

Live feed

WS /ws sends a snapshot on connect, then every event: run_started, stage, agent_start/end, branch_created, stage_advanced, pr_opened, run_finished. The SPA reconnects automatically.

Windows notePort 8000 is occupied on the author's machine, so the server runs on 8017 (uvicorn devcrew.ui.app:app --port 8017, or cmd //c run-ui.bat detached). Any free port works. Live mode needs OPENROUTER_API_KEY in .env; without it the UI shows live as unavailable and only offline runs.

8How to run it

Four ways to drive the factory. All of them work with no API key except live mode.

  1. Install dependencies (Python 3.12)
    bash
    pip install -r requirements.txt
  2. Run the deterministic demo — full pipeline, scripted model, no network
    bash
    python -m devcrew.cli demo --mode offline
  3. Watch a merge-conflict follow-up — manual merge mode stops at the PR
    bash
    python -m devcrew.cli demo --mode offline --merge-mode manual
  4. Run the trust scan — six weighted checks per role
    bash
    python -m devcrew.cli trust

Start the server (detached on Windows via the wrapper), then open the page and press Create task & run:

bash
uvicorn devcrew.ui.app:app --port 8017
# Windows detached:  cmd //c run-ui.bat
# then browse http://127.0.0.1:8017

The workspace persists at .ui-workspace/ (git repo + activity.jsonl); Reset recreates it. One run at a time — a second /api/run while busy returns 409.

The offline gate — 32 tests, no network — plus the headless UI check (server must be up):

bash
python -m tests.test_devcrew   # must print 32/32 green
python ws_smoke.py            # reset → task → run → WS events → assert merged

ws_smoke.py connects to ws://127.0.0.1:8017/ws, creates a task, starts an offline run and collects events until run_finished, then asserts the PR is merged and the task is in done.

Add a key, then the same pipeline runs on real models:

bash
cp .env.example .env   # then set OPENROUTER_API_KEY
python -m devcrew.cli demo --mode live --task "Add a delete_task function"
python examples/run_task.py "Your task"          # minimal live example
uvicorn devcrew.ui.app:app --port 8017           # UI with live mode enabled
Costs are realLive mode makes paid OpenRouter calls with per-agent monthly caps as the only ceiling. Start with the smallest task you can write.

Gotchas

  • Use the full Python path on this machine (C:\…\Python312\python.exe); bare python is not on Git Bash's PATH.
  • Scripts reconfigure stdout to UTF-8 — keep sys.stdout.reconfigure(encoding="utf-8") when adding new entry points.
  • Live mode fails fast without OPENROUTER_API_KEY — by design, there is no silent fallback to a fake model.
  • Git for Windows prints "nothing to commit" on stdout; reseeding checks the staged-diff exit code instead of message sniffing.
